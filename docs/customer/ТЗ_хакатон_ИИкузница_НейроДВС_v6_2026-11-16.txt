Техническое задание Агента Цифровой механик для хакатона «ИИ кузница»

Трек: AI-агент «Цифровой механик» для диагностики ДВС коммерческого транспорта
Заказчик: ООО «НейроДВС». Формат: онлайн, 48 часов. 
Версия 6 от 16.11.2026. Изменения к версии 5: имена полей заявки Mock ТОиР (раздел 5).
1. Задача
Автопарки коммерческого транспорта и спецтехники часто узнают о механической неисправности двигателя, когда машина уже встала: стук, потеря мощности, отказ в рейсе. Внеплановый ремонт снимает машину с линии, а износ, замеченный заранее, можно устранить в плановое ТО. Опытных мотористов, которые слышат дефект на слух, в парках мало. OBD-сканер видит ошибки электроники, механический износ он не видит.
«НейроДВС» ставит в автопарке микрофонный пост в смотровой яме. Машина заезжает на ТО, двигатель работает на холостом ходу, пост записывает звук. Записи, на которых двигатель не слышно, отбраковываются до анализа. ML-модель оценивает запись и выдаёт статус и тип отклонения. Цель — заметить отклонение до отказа, пока ремонт ещё можно запланировать.
Механику нужен понятный ответ вместо JSON: что, вероятно, не так, чем это грозит, что проверить по руководству по ремонту и как оформить заявку.
Команда делает веб-прототип AI-агента, который получает результат ML-диагностики (через заглушку), объясняет его механику, отвечает на вопросы строго по руководствам на двигатель этой машины (RAG) со ссылкой на страницу и формирует заявку на дефектовку.
Модель распознавания звука на хакатоне не обучается и не подключается. Диагноз приходит из Mock ML-сервиса по фиксированному контракту.

4. Функциональные требования
4.1. Обязательный минимум (без него проект не оценивается)
F1. Веб-интерфейс с чатом (Streamlit, Gradio или React + FastAPI).
F2. Выбор ТС из списка. Кнопка «Получить результат диагностики» вызывает Mock ML API и выводит вердикт в чат. Аудиозапись агенту не передаётся: проверка выбирается по vehicle_id и session_id.
F3. Три исхода обрабатываются по-разному: «норма» — продолжить эксплуатацию; «отклонение» — тип, уверенность, риск, рекомендация; «сбой проверки» (плохая запись) — агент не делает выводов о двигателе и просит повторить запись.
F4. Ответы на вопросы механика («Какой момент затяжки крышек коренных подшипников?», «Почему это опасно?») только по документам базы знаний, с указанием документа и страницы. Цифры нормативов агент берёт из руководства на двигатель этого ТС: модель двигателя указана в карточке ТС, норматив от другого двигателя считается ошибкой. Нет данных в базе — агент так и отвечает и рекомендует дефектовку. Рекомендуемый порядок ответа: наблюдения, гипотезы, проверки, возможный ремонт, источник, ограничения.
F5. Диагностика, RAG и заявка — отдельные инструменты агента. Агент выбирает инструмент по контексту, сценарий не зашит цепочкой if-else.
F6. URL Mock ML-сервиса и Mock ТОиР задаются переменными окружения (.env), чтобы потом подставить рабочие сервисы.
F7. Заявка на дефектовку: по команде «Создать заявку» агент формирует JSON для ТОиР (ТС, диагноз, приоритет, работы и запчасти из базы знаний, источник) и получает ticket_id от заглушки ТОиР.
4.2. Дополнительные задачи
B1. Память по vehicle_id: агент учитывает прошлые проверки и заявки этого ТС.
B2. График anomaly_score по последним 3–5 проверкам ТС.
B3. Режим «Главный механик»: сводка по парку (норма / требует внимания / карантин), приоритетный список ТС, история проверок по клику.
5. Контракты Mock API
POST /diagnose, вход: {"vehicle_id": "...", "session_id": "..."}. Выход:
{
  "vehicle_id": "M333YK47",
  "session_id": "S-0005",
  "status": "anomaly",            // normal | anomaly | check_failed
  "anomaly_type": "F08",          // F01 … F14 | null
  "anomaly_title": "Дизельная топливоподача",
  "anomaly_score": 0.76,          // 0..1
  "confidence": 0.73,             // 0..1
  "signal_quality": "good",       // good | warning | bad
  "description": "Жёсткая работа с резким стуком в цилиндрах, дымный выхлоп",
  "model_version": "mock-v1"
}
anomaly_type — идентификатор типа неисправности, условный код Mock API (в руководствах таких кодов нет): F01 клапанный механизм; F02 низкое давление масла; F03 перегрев, охлаждающая жидкость в масле; F04 ремённый привод агрегатов; F05 генератор; F06 сцепление; F07 коробка передач; F08 дизельная топливоподача; F09 турбокомпрессор, наддув; F10 компрессор пневмотормозов, насос ГУР; F11 рециркуляция отработавших газов; F12 зажигание; F13 подача бензина; F14 цепь ГРМ, гидронатяжитель. Модель двигателя в ответ не входит, она указана в карточке ТС. При status = normal поля anomaly_type и anomaly_title равны null. При status = check_failed null также anomaly_score и confidence. Коды ответа: 200 — результат; 404 — неизвестная машина или проверка; 422 — запрос не по схеме.
Mock ТОиР: POST /tickets, вход: {"vehicle_id", "session_id", "anomaly_type", "conclusion", "urgency": "low | medium | high", "operations": [...], "spare_parts": [...], "references": [{"manual": "...", "pdf_page": N}, ...]}. Выход: {"ticket_id": "TKT-0001", "status": "created"}. Все поля заявки обязательны. anomaly_type — код F01 … F14 из ответа /diagnose; conclusion — диагноз, непустая строка; urgency — приоритет; operations — работы, непустой список строк; spare_parts — запчасти, список строк, может быть пустым; references — ссылки на источники, непустой список. В каждой ссылке manual — обозначение или название документа из раздела 3, pdf_page — номер страницы PDF, от 1. Коды ответа: 201 — заявка создана; 404 и 422 — как у /diagnose.
6. Сценарии для защиты
С1. Отклонение: механик запускает проверку ТС, получает «отклонение» с типом неисправности, агент объясняет риск, даёт допуски и порядок проверки со ссылкой на страницы руководства, механик создаёт заявку.
С2. Диалог: «Можно ли своим ходом перегнать машину на базу?» — ответ по базе знаний с источником или честное «данных недостаточно».
С3. Сбой записи: проверка возвращает check_failed, агент просит повторить запись и диагноз не ставит.
С4 (если сделан B3). Главный механик видит ТС в карантине, открывает приоритетное, смотрит историю проверок.
