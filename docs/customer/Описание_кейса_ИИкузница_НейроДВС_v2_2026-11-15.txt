AI-агент «Цифровой механик»
Задача для хакатона «ИИкузница»
Заказчик: ООО «НейроДВС» Формат: 48 часов, Результат: веб-прототип и видеоролик демострации решения
1. Описание проблемы и задачи AI-агента
Коммерческий транспорт — автобусы, грузовики и спецтехника — несёт значительные потери из-за внезапных неисправностей двигателей. Механические дефекты зачастую выявляются уже после развития серьёзной поломки. Штатная электронная диагностика не всегда обнаруживает ранние признаки механического износа, а оценка звука двигателя зависит от опыта моториста.
Компания «НейроДВС» разрабатывает систему бесконтактной акустической диагностики ДВС. Специальный измерительный комплекс записывает звук работающего двигателя, а ML-модель должна выявлять отклонения от нормального акустического состояния.
Однако результат машинного анализа сам по себе недостаточен для практической работы механика. Необходимо преобразовать технические показатели в понятное заключение, помочь проверить возможную неисправность по заводской документации и организовать дальнейшее оформление дефектовки.
Задача участников — создать AI-агента «Цифровой механик», который:
Получает результаты проверки двигателя от внешнего ML-сервиса.
Объясняет механику выявленное отклонение, возможные причины и риски.
Находит в руководствах по ремонту необходимые процедуры, нормативы и рекомендации.
Отвечает на уточняющие вопросы механика на основании технической документации с указанием источника и страницы.
По подтверждению пользователя формирует структурированную заявку на дефектовку для системы технического обслуживания и ремонта (ТОиР).
Агент должен работать как интеллектуальный помощник механика, а не подменять собой специалиста, принимающего окончательное решение о состоянии двигателя.
В рамках хакатона реальная ML-модель не разрабатывается: используется предоставленный заказчиком Mock ML API.

2. Входные и выходные данные
Что агент получает на входе
От пользователя:
Выбранное транспортное средство (vehicle_id) и диагностическую сессию (session_id).
Команду получить результат диагностики.
Вопросы на естественном языке о неисправности, её последствиях, способах проверки и ремонта.
Команду создать заявку на дефектовку.
От диагностической системы:
Статус проверки: normal, anomaly или check_failed.
Тип предполагаемого отклонения.
Показатели anomaly_score, confidence и качества акустической записи.
Краткое описание выявленных признаков и версию ML-модели.
Из базы знаний заказчика:
Шесть руководств в PDF на четыре типа двигателей: ЯМЗ-236М2, ЯМЗ-536, ЗМЗ-5234.10, ЗМЗ-40904.10 и ЗМЗ-40905.10. Поиск по ним команда строит сама: готовых фрагментов, карточек неисправностей и таблицы нормативов заказчик не передаёт.
Синтетическую историю диагностических проверок 50 транспортных средств; в карточке каждого указана модель двигателя.
Что агент выдаёт на выходе
1. Диагностическое заключение для механика
Понятный результат проверки:
Норма: значимых отклонений не обнаружено.
Отклонение: описание предполагаемой неисправности, степень риска и рекомендуемые проверки.
Сбой проверки: заключение о двигателе не формируется, предлагается повторная запись.
2. Технические рекомендации
Структурированный ответ: наблюдаемые признаки → вероятные причины → необходимые проверки → возможные ремонтные действия.
Все технические нормативы и процедуры должны сопровождаться ссылками на документ и конкретные страницы. Если данных недостаточно, агент обязан сообщить об этом, а не придумывать ответ.
3. Заявка на дефектовку
Структурированный JSON с идентификатором транспортного средства, предполагаемой неисправностью, приоритетом, рекомендуемыми работами, необходимыми запчастями и ссылками на документацию.
Заявка передаётся в тестовый API системы ТОиР, которая возвращает номер заявки (ticket_id).
3. Критерии успеха за 48 часов
Обязательный результат — MVP
За время хакатона команда должна представить работающий веб-прототип, в котором:
Доступен интерфейс механика: выбор транспортного средства, чат и кнопка получения результата диагностики.
Работает подключение к Mock ML API: агент получает результат по vehicle_id и session_id и корректно обрабатывает все три статуса — норма, отклонение, некачественная запись.
Реализован RAG по руководствам: агент отвечает на вопросы о неисправностях, порядке проверки и технических нормативах по руководству на двигатель выбранной машины, указывая документ и страницу. Не допускаются вымышленные нормативы или ссылки.
Работает создание заявки: по команде механика агент формирует заявку, передаёт её в Mock ТОиР и получает номер регистрации.
Реализована агентная архитектура: диагностика, поиск в документации и создание заявки представлены отдельными инструментами. AI-агент выбирает необходимый инструмент в зависимости от запроса пользователя.
Обеспечена возможность дальнейшей интеграции: адреса внешних API задаются через конфигурацию, чтобы тестовые сервисы впоследствии можно было заменить рабочими.
Есть воспроизводимая демонстрация: команда показывает обнаружение отклонения с созданием заявки, диалог с обращением к документации и корректную обработку сбоя записи. Есть видеоролик (до 60 секунд) с демонстрацией работы агента.
Интерфейс должен быть понятен механику без подготовки, пригоден для использования на смартфоне. Команда предоставляет исходный код и инструкцию по запуску.
Дополнительные возможности — преимущество команды
А. Память по транспортному средству
Агент учитывает историю диагностических проверок и ранее созданных заявок, сопоставляет текущие результаты с предыдущими.
Б. Динамика состояния двигателя
График изменения anomaly_score по последним 3–5 проверкам с пояснением тенденции.
В. Режим главного механика
Панель состояния автопарка: распределение транспортных средств по статусам, приоритетный список требующих внимания двигателей, переход к истории конкретной машины.
Эти функции повышают практическую ценность решения, но не должны разрабатываться в ущерб обязательному функционалу.
4. Границы разработки
В задачу 48-часового хакатона не входят обучение нейросети для акустической диагностики, обработка WAV-файлов, подключение реальных производственных данных и интеграция с действующей 1С.
Все демонстрационные данные являются синтетическими.
Ожидаемый результат: работающий прототип AI-агента, архитектура которого позволяет впоследствии подключить реальные результаты ML-диагностики «НейроДВС», расширить библиотеку руководств по ремонту и интегрировать решение в процессы автопарка, продемонстрировать потенциальным пользователям алгоритм работы и возможности Агента.
